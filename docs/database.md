# Database and tenant boundaries

Apply `supabase/migrations/202610310001_core.sql` with the Supabase CLI (`supabase db push`) or the SQL editor as the project database owner. Load the idempotent question seed afterwards. This migration is intentionally a forward-only migration, not a script to re-run repeatedly. Back up existing production data before applying any future migration.

## Ownership

All private application tables carry `user_id` referencing `auth.users(id) ON DELETE CASCADE`. RLS is enabled and forced. The sole authenticated CRUD policy checks `auth.uid() = user_id` both before and after writes, preventing ownership reassignment. Anonymous access is revoked. Related private records use `(id, user_id)` composite foreign keys, so a user cannot associate their own records with another account's records. Section fact UUID arrays additionally have an ownership validation trigger. Identifiers inside document JSON are application-level references and must be validated by the CV service before generation and export.

`interview_questions` is shared immutable reference data: authenticated users may read it; only the migration/seed operator may write it. `rate_limit_windows` is internal and has no authenticated table privileges or policies. Its security-definer RPC derives the user ID from the authenticated JWT and exposes only a boolean allowance. The hard maximum is ten requests per operation per hour (thirty exports); callers cannot increase it through RPC arguments. Application code may request a lower maximum. `window_seconds` is retained for a stable API but the server enforces a fixed one-hour window to prevent alternate-window bypasses. Expired rows may be purged by a scheduled administrative task; they contain no CV or answer text.

## Canonical entities

Career identity, work experience, projects, achievements, skills, experience-skill links, education, certifications and languages are separate relational records. `career_facts` is the canonical claim registry; each statement has source type/reference, structured value when useful, verification status, confirmation timestamp and optional employer/project links. `fact_sources` preserves supporting excerpts and storage paths. Use `user_confirmed` only with `confirmed_at`; imported AI extractions start at `imported_unconfirmed`. Excluded or confidential facts are indexed separately from eligible evidence and must be filtered before AI processing and document composition.

Question answers are unique per user/question, allowing incremental upserts and later edits. A skipped answer has `status='skipped'`, not a false/negative answer. Sessions track navigation independently of answers. Job offers retain original text and structured analysis while requirements and evidence mappings remain independently queryable. CV versions retain composition JSON, language, template, approval and validation report; individual sections support ordering/hiding and evidence references. Generated-document records point to private storage objects. AI usage events contain operation/model/prompt version and usage/cost metadata, never raw prompts or professional narratives.

## Deletion semantics

Deleting an auth user cascades through all user-owned database rows, including usage events. Deleting a parent experience/project cascades through dependent records, including linked facts and evidence; the UI should warn when deleting a populated parent entity. Job deletion also deletes associated CV versions and generated-document metadata. Deleting a database row does **not** delete the underlying Storage object.

Account deletion must first recursively list and remove **all** files under the authenticated user's UUID prefix in `career-documents` with the Storage API, including uploads without a remaining fact row. Paginate listing, process nested folders and check every API result. Only after successful object removal may the server call `auth.admin.deleteUser(user.id)` using the server-only service-role key. This operation cascades relational data. If cleanup fails, retain the auth account and return a retryable error; never report success or drop the user's metadata while leaving their files behind. This sequence is not transactionally atomic across Storage and Auth: deletion failures can leave an account whose documents have been removed, so return a clear retry path. Do not delete storage metadata with SQL; that does not delete blobs.

For personal-data export, query all owner-scoped tables with the user's authenticated client, include canonical facts, sources, questionnaire answers, job analyses, CVs and usage metadata, and provide uploaded/generated documents separately or bundle them through the Storage API. Do not export service secrets or other users' data.

## Storage

The `career-documents` bucket is private, limited to PDF/DOCX MIME types and 10 MiB per object. Storage RLS requires the first path segment to equal the authenticated user's UUID for reads and writes. Examples: `<user_uuid>/imports/<random_uuid>.pdf` and `<user_uuid>/generated/<random_uuid>.docx`. Signed URLs should have short expirations. Validate extension, declared MIME, magic bytes, decompression size and extraction limits in application code: browser MIME metadata and Storage MIME restrictions do not prove a file is safe.

## Verification limits

The migration and idempotent seed are executed by `tests/database.test.ts` against PGlite, a real embedded PostgreSQL engine. The test supplies minimal Supabase-owned `auth`/`storage` schemas and JWT identity functions, strips only the pgcrypto extension declaration (UUID generation is built into PostgreSQL), and executes the production SQL otherwise unchanged. Tests use actual `SET ROLE authenticated`/`anon` and verify RLS isolation, ownership-changing write denial, composite foreign keys, storage path policies, question immutability, confirmation timestamps, deletion cascades, rate limits and concurrent queued RPC calls. These tests caught and resolved a PL/pgSQL variable/column ambiguity in the initial rate limiter. They do not verify Supabase Auth HTTP behavior, real Storage blobs, signed URLs or a remotely deployed database. Before production, apply this migration to an isolated Supabase project and repeat two-account API and storage tests, including account deletion and concurrent requests through independent database connections.
